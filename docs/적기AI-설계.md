# 적기 AI — 설계 메모

적기 행동 패턴(행동트리) 구축을 위한 **사전 검토**. 대화로만 오간 판단을 남겨둔 것이다.

> **상태: 선행 단계.** AI 관련 코드는 현재 **한 줄도 없다.** 이 문서는 이행 계획이 아니라
> §7.0의 2~3단계(요구사항 확인 · 설계 방향)에 해당한다. 페이즈 분할과 검증 계획은 아직 없다.
>
> 코드에서 직접 확인한 수치는 근거 위치를 함께 적었고, 그 외는 판단 · 추정이다.

- 관련: [ROADMAP.md](ROADMAP.md) · 프로젝트 목표는 [CLAUDE.md](../CLAUDE.md) 최상단

---

## 0. 결론 요약

1. **행동트리로 간다. 머신러닝은 쓰지 않는다.** 목표가 "이기는 AI"가 아니라 **"적당히 잘 죽어주는 AI"** 이므로, 필요한 건 성능이 아니라 **가독성과 튜닝 가능성**이다. RL은 조절 손잡이가 없다.
2. 여기서 말하는 "학습"은 ML이 아니라 **BFM/BVR 교리를 읽고 표로 정리하는 것**이다. 그 표가 곧 트리 구조가 된다.
3. 교전 패턴은 **BVR 1회 교환 → 머지 → WVR 소모전** — 워썬더 항공 RB 탑티어 구조 그대로. 저자가 원하는 것도 이것이다.
4. **BVR은 행동트리가 필요 없다.** 시작 조건과 순서가 고정이라 **페이즈 머신 6~7개 상태**로 끝난다. 본격적인 트리는 머지 이후 WVR에서만 값을 한다.
5. 난이도는 트리를 분기시키지 않고 **파라미터만** 바꾼다. BVR의 주 손잡이는 **미사일 경제**, WVR은 **반응 지연 · 시야 상실**.
6. 무장 · 센서 수치는 **실제 제원을 조사하지 않는다.** 워썬더 감각으로 근사하되, 회귀 방어선으로 **"시나리오 → 기대 결과" 표**를 쓴다.
7. **트리보다 먼저 있어야 할 것이 있다** — 비행 모델의 에너지(§7.1), 입력 추상화(§7.2), 표적 표현(§7.3). 트리는 맨 마지막이다.
8. 맵 크기는 **검토 완료 · 변경 없음**(§9).

**비목표**

- 인간 수준 또는 그 이상의 AI
- 실제 제원에 기반한 정확한 센서 · 무장 모델링
- 범용 행동트리 라이브러리 구축
- 지금 시점의 코드 작성

## 1. 왜 행동트리이고 왜 ML이 아닌가

목표를 다시 적으면: **현대 공중전 개념을 알고 있어서 만만하지 않지만, 플레이어가 작정하면 재미있게 져 주는 적기.**

RL로 학습시키면 초인적 조준 정밀도로 이기는 재미없는 상대가 나온다(DARPA AlphaDogfight가 그랬다). 무엇보다 **"이 정도로만 봐주기"를 조절할 방법이 없다.**

ML의 유일하게 합리적인 용도는 **손으로 짠 트리의 수치 임계값을 오프라인 탐색으로 튜닝**하는 것 정도이고, 그것도 한참 뒤의 얘기다.

---

## 2. 3계층 구조 — 트리는 맨 위 한 겹일 뿐

행동트리 AI가 실패하는 대부분의 원인은 트리가 나빠서가 아니라 **트리가 호출할 동사(기동)가 없어서**다.

| 계층 | 역할 | 주기 |
|---|---|---|
| **인지 (Perception)** | 기하 관계를 숫자로 — ATA, AA, 거리 R, 접근률 Vc, 에너지차 ΔEs, 피격 여부 | 매 틱 |
| **판단 (BT / 페이즈 머신)** | 상황 분류 → **기동 하나를 고름** (1~5초짜리 의도) | 10 Hz 고정 |
| **실행 (Maneuver)** | 고른 기동을 롤 / 피치 / 스로틀 명령으로 변환하는 스티어링 컨트롤러 | 매 프레임 |

핵심은 **판단 계층이 조종간을 직접 잡지 않는다**는 것. "지금은 하이 요요"까지만 정하고 실제 조종은 아래 컨트롤러가 몇 초에 걸쳐 수행한다. 이래야 기동이 인간처럼 이어져 보인다.

판단 계층을 **매 프레임이 아니라 10 Hz로** 도는 것도 의도적이다 — 싸고, 반응 지연이 공짜로 생기고, 고정 틱 시뮬레이션 방향(CLAUDE.md 멀티플레이 항목)과도 맞는다.

### 상황 분류에 필요한 숫자

- **ATA** (내 기수와 적 사이 각) · **AA** (적 기수 기준 내 위치) · **R** (거리) · **Vc** (접근률)
- 이 조합이 곧 `공세 / 수세 / 중립(정면 · 1서클 · 2서클)`. BFM 교범의 첫 장이 그대로 enum이 된다.

## 3. 교전 패턴 — 워썬더 스타일 1패스

```
동시 스폰 → 상승 / 접근 → BVR 1회 교환 → 살아남은 기체가 머지 → WVR 소모전
```

이 구조가 주는 이점:

- **BVR 구간은 분기가 적다.** 범용 반응형 트리가 아니라 페이즈 머신으로 충분하다(§4).
- **BVR 구간은 렌더링 비용이 0에 가깝다.** 지형은 카메라 거리 4500유닛(≈ 28.8 km)에서 꺼지므로, 40~80 km에서 벌어지는 BVR은 **화면에 아무것도 안 보이는 상태에서 계기만으로** 싸운다. 실제 BVR의 모습 그대로이면서 공짜다.
- **난이도 곡선이 이야기로 이어진다.** BVR에서 진 AI는 탄을 쓰고 각도를 잃은 채 자연스럽게 머지로 밀려온다. 인위적 조절 없이 WVR 국면이 열린다.

따라서 **구현 순서도 BVR이 먼저**인 편이 유리하다.

## 4. BVR — 페이즈 표

BVR은 반응이 아니라 **타임라인**이다. 전이 조건이 전부 거리 · 각도 · 시간의 숫자라 애매한 판단이 거의 없다.

| 페이즈 | 하는 일 | 이탈 조건 |
|---|---|---|
| **탐지 / 소팅** | 스캔 볼륨 안에서 컨택 획득, 누가 누구를 맡을지 배정 | 트랙 확보 |
| **인터셉트** | 오프셋 기동으로 발사 제원 확보 (충돌 코스는 오히려 회피) | 발사 조건 충족 |
| **발사** | Rmax냐 Rne냐 — **교전 성향 그 자체** | 발사 |
| **지원 (Support)** | 미사일 액티브 전까지 락 유지. 가장 위험한 구간 | A-pole 도달 |
| **크랭크** | 짐벌 한계 근처(50~60°)로 기수를 틀어 접근률만 줄이고 락은 유지 | 피격 경보 / A-pole |
| **어보트 / 드래그** | 180° 이탈. F-pole을 벌린다 | 위협 소멸 |
| **방어** | 노치(빔) + 채프 + 고도 이용. 도플러 게이트에서 사라진다 | 미사일 소멸 |
| **재교전 (Pump)** | 거리 벌린 뒤 되돌아옴 | 잔탄 · 연료 판단 |
| **머지** | WVR 트리로 인계 (§7.4) | — |

### 4.1 왜 BVR은 사실적으로 만들어도 되는가

> **WVR에서는 현실성과 재미가 싸운다. BVR에서는 안 싸운다.**

WVR은 완벽하게 기동하는 상대가 곧 못 이기는 상대다. 그래서 §5.1처럼 일부러 깎아야 한다.
BVR 교리는 **불완전한 정보와 리스크 관리**를 전제로 짜여 있다. 레이더는 놓치고, 미사일은 유한하고, 지원하려면 자기도 위험해진다. **정직하게 구현할수록 알아서 빈틈이 생긴다.**

### 4.2 레이더 모델이 곧 BVR이다

"에너지 모델 없으면 WVR이 성립 안 한다"의 BVR 판. 최소한 필요한 것:

| 요소 | 왜 필요한가 |
|---|---|
| 탐지 (RCS 대비 거리, 스캔 볼륨, 스캔 주기) | 갱신 지연 = 정보 비대칭의 출처 |
| **짐벌 한계** (기수 ±60° 정도) | **크랭크가 존재할 수 있는 유일한 이유** |
| **도플러 노치** | 없으면 BVR 방어가 없다 |
| TWS vs STT | STT를 걸면 상대 RWR이 그것을 안다 |
| **RWR** | §4.4 참조 |

### 4.3 핵심 추상화 — Transform이 아니라 **Track**

지금은 미사일이 `"Target"` 이름 문자열로 실제 오브젝트를 찾아 **진실값**을 추적한다.
BVR에서는 통째로 안 맞는다. 대신:

```
RadarTrack {
    id
    estimatedPosition, estimatedVelocity   // 진실이 아니라 추정
    quality                                 // 확정 / 메모리 트랙 / 소실
    lastUpdateTime                          // 갱신 지연
}
```

**AI도, 미사일도, HUD도, RWR도 전부 이 트랙만 읽는다. 진실값은 시뮬레이션 안에만 둔다.**

이 결정 하나가 한꺼번에 사준다:

- 노치 → 트랙 품질 저하 → 메모리 트랙 관성 예측 → 소실 (별도 코드 없이 자연 발생)
- 정보 비대칭 = 난이도 조절 (AI는 아는 것만 안다. 바보인 척할 필요가 없다)
- 채프 · 디코이 · 다중 표적 혼동을 나중에 얹을 자리
- 직렬화 가능성 · 결정론 — 트랙은 그 자체로 네트워크에 실을 수 있는 상태
- 부수 효과로 `"Target"` 이름 매칭 레거시와 파생 미사일의 null 체크 문제가 같이 정리된다

### 4.4 RWR = 적기의 판단을 플레이어에게 보여주는 창

"적기의 실수는 플레이어 눈에 보여야 한다"는 원칙이 BVR에서 성립하는 방식.
**WVR은 눈으로 보이지만 BVR은 30 km 밖이라 아무것도 안 보인다.** RWR이 없으면 플레이어는 이유도 모른 채 죽는다.

RWR로 읽혀야 하는 것: 스캔당하는 중 / **STT 락** / **발사됨** / **락이 끊겼다**(= 내 노치가 먹혔다) / 신호 방위 이동(= 크랭크 · 드래그).

> **BVR의 모든 재미는 RWR 화면 위에서 벌어진다.** UI가 아니라 게임플레이 본체다.

## 5. WVR — 기동 표

실제 BFM은 이미 정형화되어 있다. **15개 남짓이면 개싸움의 95%가 덮인다.**
진입 / 이탈 조건이 곧 트리의 Condition 데코레이터이므로, 이 표를 채우면 트리 구조는 기계적으로 나온다.

| 기동 | 진입 조건 | 이탈 조건 | 카운터 |
|---|---|---|---|
| Lead / Pure / Lag 추격 | 공세, ATA 작음, R 중 | 오버슛 임박 / 사격각 확보 | 브레이크 턴 |
| 하이 요요 | 공세인데 Vc 과다 (오버슛 위험) | 접근률 정상화 | — |
| 로우 요요 | 공세인데 각도 · 속도 부족 | 각도 회복 | — |
| 브레이크 턴 | 수세, 적이 사격권 진입 | 적이 오버슛 | 랙 추격 |
| 플랫 / 롤링 시저스 | 상호 오버슛, 저속 | 한쪽이 각도 확보 | — |
| 노치 (빔 기동) | 미사일 피격 경보 | 미사일 소멸 | — |
| 익스텐드 & 재교전 | 에너지 열세 심각 | ΔEs 회복 | 추격 |
| 스플릿-S / 임멜만 | 고도 ↔ 속도 교환 필요 | — | — |

> 나머지 항목(배럴 롤 어택, 디펜시브 스파이럴, 건 징크 등)은 필요해질 때 같은 형식으로 채운다.

### 5.1 "잘 죽어주게" 만드는 법 — WVR 편

**가장 흔한 실수: 조종 입력에 랜덤 노이즈를 섞어 약하게 만드는 것.** 이러면 약해지는 게 아니라 술 취한 것처럼 보이고, 플레이어는 "내가 이겼다"가 아니라 "쟤가 이상하다"고 느낀다.

약화는 반드시 **판단 계층에서** 한다:

| 장치 | 내용 |
|---|---|
| **반응 지연** | 상황 변화 인지 후 실제 반응까지 0.3~1.2초 |
| **결단 고착 (commitment)** | 한번 고른 기동을 N초간 바꾸지 않는다. 실제 조종사도 그렇고, 이것이 **공략 창**을 만든다 |
| **시야 상실 (tally)** | 콘 각도 + 잃어버린 시간으로 관리. 6시로 파고들면 시야를 놓치고 마지막 목격 위치로 예측 기동. **플레이어의 올바른 플레이가 곧바로 보상이 되는** 가장 깔끔한 메커니즘 |
| **에너지 오판** | 당황하면 과도한 G로 에너지를 까먹게 둔다 |
| **성능 상한** | 롤 레이트 · G 제한을 플레이어보다 살짝 낮게 |
| **차선 선택** | X% 확률로 2순위 기동을 고른다 |

## 6. 난이도 — 트리는 하나, 파라미터만 바꾼다

```
AIProfile {
    reactionTime, tallyConeDeg, tallyLossTime, commitTime, gLimit,   // WVR
    launchRangePolicy, supportDiscipline, notchAccuracy,             // BVR
    suboptimalRate, aggression
}
```

Rookie / Veteran / Ace = 이 구조체의 프리셋. **난이도로 트리를 분기시키지 않는다.**

### 6.1 BVR의 주 손잡이는 미사일 경제

재장전이 없는 1회 교전 구조에서는 이것이 다른 모든 파라미터를 압도한다.

| | 행동 | 결과 |
|---|---|---|
| Rookie | Rmax에서 전탄 투발 | 머지 시점에 **빈손** — 플레이어가 정당하게 잡음 |
| Veteran | 2발 쏘고 1발 남김 | 머지에서 한 번 더 위협 |
| Ace | Rne까지 참았다 1발, 나머지 보존 | 머지에서도 우위 |

**"적당히 잘 죽어주기"가 여기서 저절로 나온다.** 반응속도를 깎거나 주사위를 굴리지 않아도, *탄을 다 쓰고 머지에 들어온 적기*는 플레이어 입장에서 완벽히 납득 가능한 킬이고, 왜 이겼는지도 명확하다 — "쟤가 멀리서 다 쏴버렸다."

### 6.2 그 외 BVR 규율 손잡이

| 손잡이 | Rookie | Ace |
|---|---|---|
| **지원 규율** | 너무 일찍 락 해제(미사일 무력화) 또는 너무 오래 붙어 있다 피격 | A-pole 정확히 맞춰 드래그 |
| **크랭크** | 안 함 → 접근률 그대로 → 자기가 상대 사거리에 진입 | 짐벌 한계에 정확히 붙임 |
| **노치 방어** | 각도 대충 / 채프 타이밍 어긋남 | 정확히 빔 + 고도 강하 |
| **재교전** | 무작정 정면 재돌입 → 머지로 끌려감 | 펌프 후 유리한 각으로 재진입 |
| **소팅 (편대)** | 둘이 같은 표적을 쏨 → 나머지 하나가 자유 | 깔끔히 분배 |

> 노치도 채프도 **AI와 플레이어가 같은 규칙**을 쓴다. 비대칭 치팅이 없다.

## 7. 선행 인프라 — 트리는 마지막에 만든다

현 코드 기준으로 트리보다 먼저 깔아야 할 것들. **순서가 중요하다.**

### 7.1 ⓪ 비행 모델에 에너지가 없다 — 진짜 블로커

[Component/PhysicsComponent.ts](../JWFramework/Component/PhysicsComponent.ts)에 중력 · 양력 · 항력 · 속도 개념이 **전혀 없다**(해당 키워드 검색 결과 0건). 순수 트랜스폼 조작이다.

- [EditObject](../JWFramework/Object/EditObject/EditObject.ts) — `MoveForward(throttle)`
- [F16Object.ts:56](../JWFramework/Object/InGameObject/F16Object.ts#L56) — `MoveForward(15)` 고정

**에너지(속도 ↔ 고도 교환)가 없으면 요요도 익스텐드도 시저스도 의미가 없다.** BFM의 절반이 에너지 관리인데 그 기질 자체가 없다. 여기가 WVR의 시작점이다.

무장 튜닝(§8)보다도 앞에 온다 — 기체 속도 · 고도가 실체가 없으면 미사일 사거리를 감으로 맞출 기준점도 안 잡힌다.

> 참고: [PhysicsComponent.MoveForward()](../JWFramework/Component/PhysicsComponent.ts#L74-L79)가 `deltaTime`을 곱하고 있어서
> 속도 스케일 자체는 의외로 현실적이다 — `throttle` 100 = 100유닛/초 = **640 m/s (≈ Mach 1.9)**, 순항 50 ≈ **320 m/s (≈ Mach 0.94)**.

### 7.2 ① 입력 추상화 `FlightControlInput` — 구조적으로 가장 중요

지금 [F16Object.Animate()](../JWFramework/Object/InGameObject/F16Object.ts#L55-L80)는 `IsPlayer`일 때 `InputManager`를 직접 읽는다. AI가 그 자리에 들어가려면:

```
FlightControlInput { roll, pitch, yaw, throttle, fire }
    ← 플레이어 : InputManager 가 채움
    ← 적기     : 판단 계층이 채움
```

**AI가 플레이어와 똑같은 입력면을 통과해야 한다.** 회전을 직접 대입하면 (a) 치팅처럼 느껴지고 (b) CLAUDE.md가 말하는 결정론 · 직렬화 가능성이 깨진다. 워썬더가 16v16이라는 걸 생각하면 — 싱글 스테이지가 사실상 "봇으로 채운 매치"가 되므로 — 이 요구는 더 강해진다.

**이 리팩터 하나가 싱글 · 멀티 양쪽에 값을 한다.**

### 7.3 ② 표적 참조 체계

현재 미사일은 `"Target"`이라는 **이름 문자열**로 표적을 찾는다([Missile.ts](../JWFramework/Object/InGameObject/Weapons/Missile.ts)). 적기가 여럿이 각자 다른 표적을 쏘는 순간 못 버틴다. 파생 미사일들이 표적을 null 체크 없이 읽는 문제도 여기 얹혀 있다.

→ §4.3의 `RadarTrack`으로 대체한다.

### 7.4 ③ 머지 인계 계약

두 페이즈가 고정 순서로 이어지므로, **인계 상태를 미리 못 박아두면 어느 쪽부터 짜도 안 어긋난다.**

```
BVR 종료 시 WVR 트리가 물려받는 상태:
  - 잔여 무장 (종류별)
  - 에너지 상태 (속도 / 고도)
  - 트랙 품질 (상대를 보고 있는가)
  - 머지 진입 각도 우열 (누가 유리하게 들어왔는가)
  - 잔여 채프 / 플레어
```

### 7.5 ④ BT 런타임은 작게

라이브러리를 만들지 않는다. 다음이면 충분하다:

- `Sequence` / `Selector` / `Decorator(Condition · Cooldown · TimeLimit)` / `Action`
- `RUNNING` 상태를 제대로 (기동 하나가 몇 초간 RUNNING을 반환한다)
- per-AI 블랙보드 — 표적 트랙, 마지막 목격 위치, tally 타이머, 현재 기동, 에너지 상태

> AI는 매니저 싱글턴을 직접 조회하지 말고 **인지 계층이 만든 스냅샷을 읽는다.** 결정론 목표와 §3의 순환참조 부채 양쪽에 유리하다.

## 8. 파라미터 조달 — 실제 제원을 찾지 않는다

**방침: 워썬더 탑티어 감각으로 근사한다. 완벽함을 버리고 납득할 만한 재미를 택하되, 미사일별 특징은 살린다.**

타협이 아니라 정석이다. 실제 제원은 대부분 비공개이고, 공개된 값도 특정 조건 하나의 숫자라 그대로 옮겨지지 않는다. 워썬더 자체도 튜닝된 모델이다. 게다가 진짜 현실 파라미터를 넣으면 탐지 비대칭이 게임을 지배해서 재미가 없어진다. **목표는 절대적 정확도가 아니라 상대적 정확도다.**

### 8.1 절대값이 아니라 순서와 문턱값

플레이어가 인지하는 건 "9L은 18 km 나간다"가 아니라 **"9L은 정면에서도 쏠 수 있고 9H는 못 쏜다"** 이다.

기존 [Missile.ts](../JWFramework/Object/InGameObject/Weapons/Missile.ts) 파생 클래스가 이미 그 패턴이다:

| | velocityGain | velocityBreak | maxRotateSpeed | rotateSpeedAcceleration | endHoming |
|---|---:|---:|---:|---:|---:|
| AIM-9H | 40 | 1 | 18 | 5 | 100 |
| AIM-9L | 40 | 1.5 | 30 | 15 | 50 |
| R-60M | 30 | 2 | 30 | 20 | 50 |

읽어보면 성격이 살아 있다 — **9H는 둔하게 돌지만 멀리 활공하고, 9L은 세게 돌고, R-60M은 즉각 꺾이지만 에너지를 빨리 까먹는다.** 감으로 맞춘 값인데 각 미사일의 실제 캐릭터와 방향이 맞는다. 이 방식을 그대로 확장한다.

> ⚠️ `maxVelocity`가 셋 다 **80으로 동일**해서 사거리 차별화가 전적으로 감속률에만 걸려 있다. 안 쓰고 있는 축 = 여유분.

### 8.2 남은 절반은 시커다

위 표는 운동 성능만 차별화한다. 정작 IR 미사일의 성격을 결정하는 시커가 통째로 없다 — 미사일이 표적을 알고 그냥 쫓아간다.

```
IRSeeker {
    allAspect        // 전방위 조준 가능 여부  ← 9L과 9H를 가르는 단 하나의 값
    fovDeg           // 락온 가능 원뿔
    gimbalDeg        // 락 유지 한계 (넘으면 놓침)
    flareResistance  // 0~1
    minRange         // 신관 무장 거리
    lockTimeSec
}
```

**`allAspect` 불리언 하나가 위 파라미터 표 전체보다 미사일 성격을 크게 가른다.** 투자 대비 효율이 가장 좋은 지점.

### 8.3 회귀 방어선 — 시나리오 표

"감으로 조절"의 유일한 위험은 **숫자가 표류해도 알 수 없다**는 것이다. 해법:

> **스펙을 파라미터가 아니라 "시나리오 → 기대 결과" 표로 쓴다.**

```
S1  정면 8 km, 동고도, 양측 Mach 0.9      → 9L 명중 / 9H 락 불가
S2  후미 3 km, 표적 5G 선회                → 9L · R60M 명중, 9H 실패
S3  후미 3 km, 표적 플레어 1회             → R60M 회피됨, 9L 명중
S4  후미 3 km, 표적 노치                   → 레이더탄 트랙 소실
S5  비기동 표적, 명중하는 최대 거리         → 9H > 9L > R60M
```

**절대 수치가 아니라 행동 결과가 스펙이 된다.** 파라미터를 감으로 흔들어도 회귀가 잡히고, 미사일을 추가할 때 "어디쯤 놓을지"도 이 표 위의 위치로 정해진다.

자동 테스트가 없는 프로젝트라 이런 수동 시나리오 표가 사실상 유일한 회귀 방어선이며, **§7.0의 5단계(테스트 짜기) 산출물 역할을 겸한다.** 에디터가 있으니 시나리오용 `Scene.json`을 만들어두면 재현도 쉽다.

**튜닝 규칙 두 개**: 한 번에 한 축만 바꾼다 · 바꾸면 시나리오 표를 다시 돌린다.

### 8.4 시스템별 "플레이어가 실제로 느끼는 숫자"

여기에만 공을 들이고 나머지는 대충 해도 티가 안 난다.

| 시스템 | 정성껏 맞출 것 | 대충 해도 되는 것 |
|---|---|---|
| 레이더 | **노치 각도 폭** — 플레이어 방어 기술의 전부 | 탐지거리, 스캔 패턴, RCS |
| IR 시커 | **플레어 저항** — 플레어 누른 게 먹히느냐 | 시커 감도, 열원 모델 |
| 미사일 | **최소 사거리 + 기동성/사거리 트레이드오프** | 추력 곡선, 항력 계수 |

### 8.5 근사하면 안 되는 것

- **플레이어 피드백은 정확해야 한다.** 미사일 성능은 근사해도 되지만 *언제 락됐는가 / 언제 발사됐는가 / 언제 놓쳤는가*가 애매하면 플레이어가 판단을 못 한다. 그러면 튜닝을 아무리 잘해도 재미가 안 난다. **근사의 대상은 물리지 피드백이 아니다.**
- **AI와 플레이어가 같은 무장 코드 · 같은 파라미터를 쓸 것.** 조금이라도 비대칭이면 치팅으로 느껴진다(§7.2와 같은 이유).
- **최소 사거리와 신관 무장 거리.** 너무 가까우면 안 맞는다는 규칙이 없으면 머지 후 WVR이 무너진다.

## 9. 맵 크기 — 검토 완료, 변경 없음

BVR 사거리 대비 맵이 좁지 않은지 검토했고, **결론은 지금 그대로 둔다.**

### 실측

[ModelLoadManager.ts:156-177](../JWFramework/Manager/ModelLoadManager.ts#L156-L177) — `LoadHeightmapTerrain(20, 20)`, `tileSize = 900`.
§4.7 환산으로 **1유닛 = 6.4 m**.

| | 유닛 | 실거리 | 면적 |
|---|---:|---:|---:|
| 전체 격자 20×20 | 18,000 | **115.2 km** | **13,271 km²** |
| 더미 테두리 제외 18×18 | 16,200 | 103.7 km | 10,750 km² |
| 참고: 경기도 | | | ~10,200 km² |

**실사용 영역이 경기도와 거의 같고, 전체로는 1.3배.** 남한 전체의 13%다.

### 판단

이 크기는 **처음부터 워썬더 항공 맵(대략 64~128 km) 기준으로 의도해서 정한 값**이다. 지리적으로 작지 않다.

BVR이 소모하는 건 면적이 아니라 **축의 직선거리**이고, 예산을 뽑으면 이렇다:

```
탐지(~80 km) → 발사(~40 km) → 크랭크/지원 → 드래그      ≈ 축 50~60 km
펌프 후 재교전                                          ≈ 축 80 km 추가
──────────────────────────────────────────────────────
합계 ≈ 140 km   >   한 변 115 km (대각선 163 km)
```

즉 **1회 교전은 충분하고, 재교전 1회는 대각선을 알뜰히 써야 겨우 들어간다.** 그런데 그게 바로 §3의 목표 패턴이고, 종심이 얕은 한반도 공역의 실제 모습이기도 하다.

맵 확장 비용도 싸지 않다 — 40×40이면 타일이 400 → 1600개로 4배가 되고 터레인 성능 작업이 그대로 부담을 받는다.

| 선택 | 필요한 것 |
|---|---|
| **1회 교전 → 머지** (채택) | 없음. 지금 맵으로 성립 |
| 반복 교전 | 교전 영역 리셋 / 랩어라운드 / 지형 스트리밍 중 하나 |

> **반복 교전은 나중에 원하면 얹는 옵션이지 전제 조건이 아니다.**

## 10. 정리 — 확정된 것과 미결

| 항목 | 상태 |
|---|---|
| 맵 크기 | **확정** — 변경 없음 (§9) |
| 교전 패턴 | **확정** — BVR 1회 → 머지 → WVR (§3) |
| BVR 구현 형태 | **확정** — 페이즈 머신. 행동트리는 WVR만 (§4, §5) |
| 난이도 손잡이 | **확정** — BVR은 미사일 경제, WVR은 반응 지연 · 시야 상실 (§6) |
| 파라미터 조달 | **확정** — 감으로 튜닝 + 시나리오 표 (§8) |
| ML 사용 | **확정** — 쓰지 않음 (§1) |
| `FlightControlInput` · `RadarTrack` · 인계 계약 | **형태 미정** (§7.2~7.4) |
| 비행 모델 에너지 | **미해결. WVR의 진짜 블로커** (§7.1) |

### 착수 순서 (제안)

```
0. 비행 모델 에너지            ← 이게 없으면 그 아래가 전부 무의미
1. FlightControlInput 추상화
2. RadarTrack 추상화
3. 레이더 / RWR / IR 시커 모델 + 중거리탄(2단 유도)
4. BVR 페이즈 머신
5. WVR 기동 라이브러리 → 행동트리
```

**행동트리는 맨 마지막이다.**

착수 시점에 이 문서는 §7.0 3단계(설계) 입력으로 쓰고, 4단계(페이즈 계획) · 5단계(검증 계획)를 그때 새로 작성한다.
