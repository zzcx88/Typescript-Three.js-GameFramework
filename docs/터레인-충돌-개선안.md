# 터레인 · 충돌 개선안

> 2026-08-03 조사. 코드 변경 없음.
> 문제의식: **격자로 400장 쪼개놓고, 그 격자를 공간 인덱스로 전혀 쓰지 않는다.**

## 0. 현재 격자의 실체

[ModelLoadManager.LoadHeightmapTerrain(20, 20)](../JWFramework/Manager/ModelLoadManager.ts#L156)

```
타일 400장 = 20 × 20,  피치 900,  타일 j 의 범위 = [j*900-450, j*900+450]
경계 76장 = dummy (세그먼트 1×1, 콜라이더 없음)
내부 324장 = 세그먼트 16×16 → 정점 289개, 삼각형 512개
저장 = objectList[OBJ_TERRAIN] 의 평면 배열, 인덱스 = 생성 순서 = i*row + j
```

**월드 좌표 → 타일 인덱스는 나눗셈 두 번이면 끝난다.**

```ts
const j = Math.round(x / 900);
const i = Math.round(z / 900);
const index = i * row + j;      // O(1)
```

그런데 이 계산이 **코드 어디에도 없다.** 격자가 있는데 선형 탐색을 한다 — 이게 문제의 뿌리다.

## 1. A군 — 격자를 공간 인덱스로 쓰기 (핵심)

### A-1. 광역 페이즈 전수 루프 제거 ★ 최우선

[ObjectManager.Animate():257-263](../JWFramework/Manager/ObjectManager.ts#L257)

```ts
CollideSphereToBox(objectList[OBJ_OBJECT3D], 비-dummy 터레인)   // N × 324
CollideSphereToBox(objectList[OBJ_MISSILE],  비-dummy 터레인)   // M × 324
```

오브젝트 하나가 **자기가 올라선 타일을 찾으려고 324장 전부와 sphere-box 교차 검사**를 한다. 오브젝트 50개면 프레임당 16,200회.

→ `WorldToTerrainIndex(x, z)` 로 **O(1) 배정**. 스피어 반지름이 타일보다 작으면 자기 타일 + 인접 8장만 보면 되고, 대부분은 자기 타일 하나로 끝난다.

> 이게 `inSectorObject` 가 원래 하려던 일이다. 지금은 **광역 페이즈를 없애려고 만든 자료구조를 광역 페이즈 전수 검사로 채우고 있다.**

### A-2. 지면 스냅을 레이캐스트에서 하이트필드 샘플링으로

[CollideRayToTerrain()](../JWFramework/Manager/CollisionManager.ts#L25) 은 오브젝트마다 `Raycaster.intersectObject(타일 메시)` 를 부른다 → 512 삼각형 순회. 못 맞히면 y=2000 에서 **한 번 더** 쏜다.

격자는 규칙적이므로 높이는 **바이리니어 보간으로 직접 계산**할 수 있다:

```
타일 로컬 uv → 정점 격자 (17×17) 의 네 꼭짓점 → 보간
```

레이캐스트 0회, 삼각형 순회 0회, 재시도 분기 불필요. 지형 위 어디서든 항상 답이 나온다.

### A-3. 피킹 — 격자 DDA 레이 마칭 ★ 누락되어 있던 항목

**A-1 은 피킹을 해결하지 못한다.** `WorldToTerrainIndex(x, z)` 는 월드 좌표를 이미 알 때 쓰는 것이고, 피킹은 화면 좌표에서 출발하는 레이라 좌표를 미리 모른다.

현재 [Picker.Pick():148](../JWFramework/Picker/Picker.ts#L148) 는 픽 한 번에 **타일 400장 전부**를 레이캐스트한다(내부 타일은 512 삼각형씩). `.map()` 으로 400칸 배열도 매번 새로 만든다. `T` 브러시 드래그면 매 프레임이다.

> **거리 컬링은 여기에 아무 도움이 안 된다.** three 의 `Raycaster` 는 `visible` 을 보지 않고 `layers` 만 검사한다:
> ```js
> if ( object.layers.test( raycaster.layers ) ) {
>     const result = object.raycast( raycaster, intersects );
> ```
> [Animate():365](../JWFramework/Object/CommonObject/Terrain/HeightmapTerrain.ts#L365) 가 `visible = false` 로 꺼놓은 타일도 전부 레이캐스트된다.

→ 균일 격자이므로 **레이가 지나는 타일만 앞에서부터 순서대로 훑고 첫 히트에서 멈춘다**(복셀 DDA). 보통 몇 장이면 끝나고, 카메라에서 먼 지형도 정확히 찍힌다. A-1 과 같은 인덱스 체계를 공유한다.

**중간 단계**: 타일마다 이미 `CollisionComponent.BoundingBox` 가 있으니, 레이 대 AABB 400회(매우 쌈)로 거른 뒤 맞은 것만 거리순으로 메시 레이캐스트하고 첫 히트에서 멈춘다. DDA 보다 훨씬 간단하고 효과의 대부분을 가져간다.

> DDA 자체의 원리·구현·다른 쓰임새는 **[부록 A](#부록-a--격자-dda-레이-마칭)** 에 정리했다. 피킹 말고도 쓸 곳이 여럿이다.

### A-4. 타일을 LOD · 컬링 단위로

[HeightmapTerrain.Animate():362-372](../JWFramework/Object/CommonObject/Terrain/HeightmapTerrain.ts#L362) 가 카메라 거리 4500 으로 `visible` 을 끈다. 격자 인덱스를 쓰면 **카메라 타일 기준 반경 k 링만 순회**하면 되고, 거리별로 세그먼트 수를 낮춘 지오메트리로 교체하는 LOD 도 같은 축에서 나온다.

## 2. B군 — 프레임 루프의 할당

매 프레임 새 배열/벡터를 만드는 지점들. 전부 GC 압력이다.

| 위치 | 내용 | 프레임당 |
|---|---|---|
| [ObjectManager.ts:259,263](../JWFramework/Manager/ObjectManager.ts#L259) | `filter(IsDummy == false)` — **불변인데 매 프레임 재계산** | 400 스캔 × 2 + 배열 2개 |
| [ObjectManager.ts:265](../JWFramework/Manager/ObjectManager.ts#L265) | `filter(inSector == true)` | 400 스캔 + 배열 1개 |
| [ObjectManager.ts:267](../JWFramework/Manager/ObjectManager.ts#L267) | `filter(IsClone)` | 배열 1개 |
| [HeightmapTerrain.ts:355](../JWFramework/Object/CommonObject/Terrain/HeightmapTerrain.ts#L355) | `inSectorObject.filter(IsDead == false)` — **타일마다** | 배열 최대 400개 |
| [HeightmapTerrain.ts:362](../JWFramework/Object/CommonObject/Terrain/HeightmapTerrain.ts#L362) | `GetPosition().clone()` — **타일마다** | Vector3 400개 |
| [CollisionManager.ts:70](../JWFramework/Manager/CollisionManager.ts#L70) | `filter().map()` 이 **바깥 루프 안에** 있다 | 물 타일 수만큼 |

조치: dummy/비-dummy 분리는 **생성 시 한 번** 확정해 캐시. `inSectorObject` 정리는 filter 대신 swap-remove. 거리 비교는 재사용 벡터 + `distanceToSquared()`(제곱근 제거).

## 3. C군 — `SetHeight()` 의 알고리즘 문제 ★ 브러시 렉의 주범

[HeightmapTerrain.SetHeight():262-285](../JWFramework/Object/CommonObject/Terrain/HeightmapTerrain.ts#L262)

정점 **하나**를 고친 뒤 텍스처 판정을 위해 **289개 정점을 전부 순회**하는데, 그 루프 안에서:

```ts
if (cnt >= 30 && this.physicsComponent.GetMaxVertex().y <= 110)
```

[`GetMaxVertex()`](../JWFramework/Component/PhysicsComponent.ts#L118) 는 **자식 지오메트리의 모든 정점을 traverse** 한다(289개). 즉 **289 × 289 ≈ 83,000 정점 읽기**.

[Picker](../JWFramework/Picker/Picker.ts#L153) 는 `face.a/b/c` 로 `SetHeight` 를 **3번** 부른다 → **한 번 클릭에 약 25만 정점 읽기.** `T` 브러시 드래그면 이게 매 프레임이다.

→ 조치:
- `GetMaxVertex()` 를 루프 밖으로. 애초에 최대 높이는 `SetHeight` 가 **증분으로 추적**할 수 있다
- 텍스처 판정도 증분 카운터로 (전수 순회 불필요)
- `Picker` 는 3개 정점을 한 번에 넘기고 판정은 마지막에 1회

### C-1. `useDirtTexture` 가 한 번 켜지면 안 꺼진다 (버그)

```ts
if (getY(i) <= -3) useDirtTexture = true;
else if (i == positionLength - 1 && !useDirtTexture) useDirtTexture = false;
```

else 분기는 **이미 false 일 때만** false 를 넣는다. 지형을 깎아 사막 텍스처가 켜지면 **다시 올려도 되돌아오지 않는다.**

### C-2. `computeBoundingSphere()` 갱신 누락

[생성 시 1회](../JWFramework/Object/CommonObject/Terrain/HeightmapTerrain.ts#L116)만 호출된다. `computeVertexNormals()` 는 [변경 시 갱신](../JWFramework/Object/CommonObject/Terrain/HeightmapTerrain.ts#L351)되는데 바운딩 스피어만 빠졌다.

평평한 900×900 평면의 스피어는 중심이 타일 원점, 반지름 `√(450²+450²) ≈ 636` 이다. **모서리 정점 (450, 450) 이 이미 반지름에 딱 걸쳐 있어** 조금만 올려도 밖으로 나간다. 그 결과 낡은 경계가 **두 곳에서** 쓰인다:

- **프러스텀 컬링** — 산을 높이 세우면 화면 가장자리에서 타일이 사라진다
- **피킹** — three 의 `Mesh.raycast` 가 같은 스피어로 조기 탈출하므로, **스피어를 스치지 않는 각도의 레이는 높인 봉우리를 못 맞힌다** (→ [부록 A.4](#a4-실제-이득이-어디서-오는가))

편집 단위가 ±1 이라 평소엔 잘 안 드러나지만, 산을 높이 세우고 낮은 각도로 볼 때 나타나는 종류의 버그다. `SetHeight` 에서 `vertexNormalNeedUpdate` 와 같은 타이밍에 갱신하면 된다.

## 4. D군 — 죽은 코드 · 잠복 버그

### D-1. `cameraInSector` — 고치지 말고 **삭제한다**

[CollisionActive():295](../JWFramework/Object/CommonObject/Terrain/HeightmapTerrain.ts#L295) 과 [CollisionDeActive():313](../JWFramework/Object/CommonObject/Terrain/HeightmapTerrain.ts#L313) **양쪽 다 `false` 를 넣어서** 절대 `true` 가 되지 않는다. 따라서 [`GetInSectorTerrain()`](../JWFramework/Manager/ObjectManager.ts#L47) 은 언제나 빈 그룹을 반환하고, 호출부 3곳은 전부 주석 처리되어 있다.

원래 의도는 **피킹 후보를 카메라 주변 타일로 줄이는 것**이었다. 하지만 살릴 가치가 없다:

1. **필터 기준이 틀렸다.** 카메라 근접 ≠ 레이가 닿는 범위. 지평선을 보면 레이는 카메라 섹터를 한참 넘어가므로 **먼 지형을 못 찍게 된다**
2. **유지 비용.** 플래그 하나 세우려고 카메라 대 터레인 광역 페이즈가 필요한데, 그 패스(`CollideBoxToBox(TERRAIN, CAMERA)`)는 [주석 처리](../JWFramework/Manager/ObjectManager.ts#L254)되어 있다
3. **살려도 망가진다.** `Object3D.add()` 는 내부에서 `object.removeFromParent()` 를 호출한다. `GetInSectorTerrain()` 은 타일을 **씬에서 떼어내** `terrainList` 그룹으로 옮기는데, 그 그룹은 한 번도 비워지지 않는다 → 타일이 누적되고 돌아오지 않는다

→ `cameraInSector` · `GetInSectorTerrain()` · `ObjectManager.terrainList` **셋 다 제거.** 원래 목적은 **A-3(격자 DDA)** 이 정면으로 해결한다.

> 오브젝트 쪽 `inSector` / `inSectorObject` 는 **유지한다.** 이건 살아 있고 좁은 페이즈에 실제로 쓰인다. A-1 에서 채우는 방식만 바뀐다.

### D-2. 이웃 인덱스 계산이 정사각 격자에서만 맞는다

인덱스는 `i*row + j` 이므로 z 방향 이웃은 `index ± row` 다. 그런데 [코드는 `± this.col` 을 쓴다](../JWFramework/Object/CommonObject/Terrain/HeightmapTerrain.ts#L242).
`row == col == 20` 이라 지금은 우연히 맞는다. **직사각 격자로 바꾸는 순간 이음매가 깨진다.**

### D-3. `HeightBuffer` getter 의 pop 루프

```ts
for (let i = 0; i < this.heightBuffer.length; ++i) this.heightBuffer.pop();
this.heightBuffer.length = 0;
```

`length` 가 줄어드는 배열을 `i < length` 로 돌아 **절반만 지우고**, 그 다음 줄이 어차피 전부 지운다. 첫 루프는 통째로 불필요.

### D-4. 매 프레임 유니폼 재대입

[Animate():339-346](../JWFramework/Object/CommonObject/Terrain/HeightmapTerrain.ts#L339) 이 타일 324장의 텍스처 유니폼을 **값이 안 바뀌어도** 매 프레임 대입한다. 플래그가 바뀔 때만 하면 된다.

### D-5. 안 보이는 것이 찍힌다 (버그)

거리 컬링은 **전부 렌더 가시성 전용**이고 피킹에는 관여하지 않는다.

| 위치 | 대상 | 임계 |
|---|---|---|
| [HeightmapTerrain.ts:365](../JWFramework/Object/CommonObject/Terrain/HeightmapTerrain.ts#L365) | 터레인 타일 | 4500 |
| [EditObject.ts:181](../JWFramework/Object/EditObject/EditObject.ts#L181) | 오브젝트 + 라벨 + OBB 헬퍼 | 3000 |
| [LowCloud.ts:102,121](../JWFramework/Object/InGameObject/LowCloud.ts#L102) | 구름 덩이 / 인스턴스 | 6000 / 200 |

셋 다 `.visible` 만 끄는데 **`Raycaster` 는 `visible` 을 보지 않는다**(A-3 참조). 결과:

- `4`(삭제) 모드에서 **빈 화면처럼 보이는 곳을 클릭하면 안 보이는 오브젝트가 지워진다**
- `1`(선택) 모드에서 안 보이는 오브젝트가 선택되어 SRT 패널이 붙는다
- `3`(터레인) 모드에서 4500 너머의 안 보이는 타일이 편집된다

→ 컬링 판정을 `visible` 뿐 아니라 **피킹 후보 목록에도** 반영해야 한다. A-3(AABB 선별 / DDA)에서 후보를 만들 때 같은 기준을 적용하면 자연스럽게 해결된다.

### D-6. 피킹 경로의 반복 할당

- [`PickableObjectList`](../JWFramework/Manager/ObjectManager.ts#L63) getter 는 접근마다 filter 3 + concat 2 + filter 1 = **배열 6개**를 새로 만든다. 호출부에서 `.map()` 이 하나 더 붙는다
- 터레인 픽 3곳은 매번 `objectList[OBJ_TERRAIN].map(...)` 으로 **400칸 배열**을 만든다
- 브러시 드래그(`T`)는 [EditScene.ts:219,258](../JWFramework/Scene/EditScene.ts#L219) 에서 **매 프레임** `SetPickPosition()` → `Pick()` 을 부른다 → 위 할당이 전부 프레임 비용이 된다

### D-7. 디버그 잔재

[CollisionComponent.Update():208](../JWFramework/Component/CollisionComponent.ts#L208) — `OBJ_MISSILE` 마다 매 프레임 `console.log`. CLAUDE.md §2③ 에 적힌 그대로 아직 살아 있다.

## 5. 제안 순서

각 단계는 독립적으로 되돌릴 수 있고, 앞 단계가 뒤 단계의 전제가 되지 않게 배치했다.

| 단계 | 내용 | 기대 효과 | 위험 |
|---|---|---|---|
| **1** | D군 정리 (D-1 ~ D-4, D-7) + C-1 버그 | 동작 정상화. 코드량 감소 | 낮음. D-1 은 되살리는 게 아니라 **삭제**라 회귀 위험이 없다 |
| **2** | C군 — `SetHeight` 증분화 | **브러시 조작 체감이 가장 크게 바뀐다** | 중. 텍스처 판정 결과가 달라질 수 있음 |
| **3** | B군 — 할당 제거 | GC 스파이크 감소 | 낮음. 순수 최적화 |
| **4** | A-3 중간 단계 — 피킹을 AABB 로 선별 후 첫 히트에서 중단 + **D-5·D-6 동시 해결** | **브러시 드래그가 다시 크게 개선**, 안 보이는 것이 찍히는 버그도 사라짐 | 낮음. 후보만 줄이고 컬링 기준을 공유한다 |
| **5** | A-1 — `WorldToTerrainIndex` 도입, 광역 페이즈 교체 | **프레임당 충돌 검사 수가 자릿수로 감소** | 중. 섹터 등록 경로가 바뀜 |
| **6** | A-3 본단계 — 격자 DDA 레이 마칭 | 피킹이 지나는 타일 수에만 비례 | 중 |
| **7** | A-2 — 하이트필드 샘플링 | 지면 스냅 레이캐스트 제거 | 중. 스냅 위치가 미세하게 달라짐 |
| **8** | A-4 — 타일 LOD | 원거리 정점 수 감소 | 중 |

**1~4 는 눈에 보이는 동작이 바뀌면 안 된다.** 5~8 은 구조 변경이라 각 단계마다 브라우저 확인이 필요하다.

> 4번을 5번보다 앞에 둔 이유 — 브러시 렉의 원인이 두 갈래(C군의 `SetHeight` 전수 순회, A-3 의 400장 레이캐스트)인데 **둘 다 피킹 경로**다. 2번과 4번을 연달아 처리하면 같은 증상을 한 번에 끝낼 수 있다.

### 측정 방법

자동 테스트가 없으므로 **숫자를 먼저 고정**한다. `P` 키가 이미 `renderer.info` 와 삼각형 수를 출력하니, 여기에 다음을 붙이면 단계별 비교가 가능하다:

- 프레임당 sphere-box 검사 횟수 (A-1 전후)
- `SetHeight` 1회 소요 시간 (C군 전후)
- Stats 패널의 FPS · MS, 브러시 드래그 중 최저 FPS

## 6. 부록 A — 격자 DDA 레이 마칭

레이가 격자를 지날 때 **어느 칸을 어떤 순서로 지나는지**를 정확히 계산하는 알고리즘. 선 긋기의 Bresenham 을 일반화한 것으로, 복셀 렌더링에서 Amanatides & Woo 방식으로 알려져 있다.

```
지금:  400장 전부에게 "너 맞았니?" → 맞은 것 모아 거리순 정렬 → 첫 번째
DDA :  레이가 실제 지나는 칸만 가까운 쪽부터 방문 → 맞는 순간 멈춤
```

**핵심은 순서다.** 앞에서부터 방문하므로 처음 맞은 것이 곧 최근접이다. 정렬이 필요 없고 나머지를 볼 이유도 없다.

### A.1 원리

터레인은 하이트필드이므로 **y 를 빼고 XZ 2D 격자**로 다룬다.

```
        j=3   j=4   j=5   j=6   j=7
      ┌─────┬─────┬─────┬─────┬─────┐
 i=2  │     │     │     │     │     │
      ├─────┼─────┼─────┼─────┼─────┤
 i=3  │  O──┼─→   │     │     │     │     O = 레이 시작
      ├─────┼──╲──┼─────┼─────┼─────┤
 i=4  │     │   ╲ │     │     │     │
      ├─────┼─────╲─────┼─────┼─────┤
 i=5  │     │     │ ╲   │  ✱  │     │     ✱ = 히트
      └─────┴─────┴─────┴─────┴─────┘

 방문: (3,3) (3,4) (4,4) (5,4) (5,5) (5,6)✱ → 종료
 → 6장. 나머지 394장은 쳐다보지도 않는다.
```

한 칸을 건너는 데 드는 레이 파라미터 `t` 의 증분을 축마다 미리 구해두고, **다음 경계가 더 가까운 축으로만 한 칸 전진**한다.

### A.2 이 프로젝트 수치로

타일 크기 900, 타일 `j` 의 범위는 `[j*900-450, j*900+450]`. **+450 이동**시키면 경계가 900 의 배수에 떨어져 `floor` 로 바로 인덱스가 나온다.

```ts
// 격자 좌표 — 셀 j 가 [j, j+1) 을 차지하게 된다
const gx = (origin.x + 450) / 900;
const gz = (origin.z + 450) / 900;

let j = Math.floor(gx);
let i = Math.floor(gz);

const stepJ = dir.x > 0 ? 1 : -1;
const stepI = dir.z > 0 ? 1 : -1;

// 한 칸 건너는 데 드는 t
const tDeltaX = dir.x !== 0 ? Math.abs(900 / dir.x) : Infinity;
const tDeltaZ = dir.z !== 0 ? Math.abs(900 / dir.z) : Infinity;

// 첫 경계까지의 t (부호는 자동으로 양수가 된다)
const nextGx = dir.x > 0 ? j + 1 : j;
const nextGz = dir.z > 0 ? i + 1 : i;
let tMaxX = dir.x !== 0 ? ((nextGx - gx) * 900) / dir.x : Infinity;
let tMaxZ = dir.z !== 0 ? ((nextGz - gz) * 900) / dir.z : Infinity;
```

전진 루프는 이게 전부다:

```ts
while (j >= 0 && j < this.row && i >= 0 && i < this.col)
{
    const tile = terrainList[i * this.row + j];
    if (tile != null && tile.IsDummy == false)
    {
        const hit = this.RaycastTile(tile);
        if (hit != null)
            return hit;          // 앞에서부터 왔으므로 이것이 최근접
    }

    if (tMaxX < tMaxZ) { j += stepJ; tMaxX += tDeltaX; }
    else               { i += stepI; tMaxZ += tDeltaZ; }
}
return null;
```

`tMaxX < tMaxZ` 비교 하나가 "다음에 만날 경계가 세로선이냐 가로선이냐"를 판정한다. 나눗셈은 루프 밖에서 끝났고 안에는 **덧셈과 비교만** 남는다.

> 인덱스 식 `i * this.row + j` 는 **D-2 를 고친 뒤**의 것이다. 현재 코드의 `± col` 관례를 그대로 쓰면 직사각 격자에서 어긋난다.

### A.3 실무 디테일

**① 레이가 격자 밖에서 시작한다.** 카메라는 보통 지형 위 하늘에 있고 격자 바깥일 수도 있다. 먼저 레이를 격자 전체 AABB 에 클리핑해 **진입점부터** 시작한다. 아예 안 만나면 즉시 종료.

**② 축평행 레이.** `dir.x == 0` 이면 `900/0` 이 `Infinity` 가 되어 자연스럽게 처리되지만, 정확히 경계 위에서 시작하면 `0/0 = NaN` 이 나올 수 있어 위처럼 명시적으로 막는다.

**③ 하이트필드 조기 탈출 — 여기가 진짜 이득이다.** 타일마다 **최대 높이**를 들고 있으면, 레이가 그 타일 구간을 지나는 동안 y 가 계속 최대 높이보다 위면 **삼각형 검사 없이 건너뛴다.** 하늘에서 비스듬히 내려다보는 대부분의 경우 앞쪽 타일이 전부 이걸로 걸러진다.

> 이 "타일별 최대 높이"는 **C군에서 어차피 만들어야 하는 값**이다. `SetHeight` 의 `GetMaxVertex()` 전수 순회를 증분 추적으로 바꾸면 나오는 게 정확히 이것이다. 두 작업이 같은 자료를 공유한다.

### A.4 실제 이득이 어디서 오는가

정확히 하자면 **현재 코드가 400 × 512 삼각형을 다 도는 것은 아니다.** three 의 `Mesh.raycast` 는 `geometry.boundingSphere` 로 먼저 거른다(`three.core.js` 의 `Mesh.raycast`). 실제 이득은 다른 데서 온다:

| | 지금 | DDA |
|---|---|---|
| 후보 배열 | `.map()` 으로 **400칸 배열을 매 픽**(브러시면 매 프레임) | 없음 |
| 스피어 테스트 | 400회 | 지나는 칸 수만 (보통 5~15) |
| 정렬 | 맞은 것 전부 정렬 | 불필요 (앞에서부터 옴) |
| 안 보이는 것이 찍힘 | 발생 (D-5) | 후보 생성 시 같은 기준 적용 가능 |

> **스피어 조기 탈출이 지금 버그를 만들고 있다.** 평평한 900×900 평면의 바운딩 스피어 반지름은 `√(450²+450²) ≈ 636` 이고 중심은 타일 원점이다. **모서리 정점 (450, 450) 이 이미 반지름에 딱 걸쳐 있어** 조금만 올려도 스피어 밖으로 나간다. C-2 대로 `computeBoundingSphere()` 가 갱신되지 않으므로, 높인 봉우리는 스피어 밖에 놓이고 **스피어를 스치지 않는 각도의 레이는 그 봉우리를 못 맞힌다.** 프러스텀 컬링도 같은 스피어를 쓴다. 편집 단위가 ±1 이라 평소엔 잘 안 드러나지만, 산을 높이 세우고 낮은 각도로 볼 때 나타나는 종류의 버그다.

### A.5 피킹 말고 쓸 곳

같은 순회 코드를 재사용할 수 있는 지점들. **하이트필드 위의 선분 질의**는 전부 여기에 해당한다.

**지금 바로 쓸 수 있는 것**

| 용도 | 현재 상태 |
|---|---|
| **3인칭 카메라 지형 관통 방지** | [Camera](../JWFramework/Object/Camera/Camera.ts#L26) 는 이미 `CreateBoundingBox(300, 1, 300)` 을 만들고 매 프레임 `Update()` 까지 하는데, **그걸 쓰는 패스**(`CollideBoxToBox(TERRAIN, CAMERA)`)가 [주석 처리](../JWFramework/Manager/ObjectManager.ts#L254)되어 있다. 타겟 → 카메라 선분을 DDA 로 훑어 막히는 지점까지 카메라를 당기면 된다 |
| **지면 스냅의 순간이동 폴백 제거** | [CollideRayToTerrain](../JWFramework/Manager/CollisionManager.ts#L45) 은 아래로 쏴서 못 맞히면 **y=2000 에서 다시 쏴 지면으로 순간이동**시킨다. 이전 프레임 위치 → 현재 위치 **선분**을 훑으면 "이번 프레임에 지면을 통과했는가"를 정확히 판정할 수 있어 폴백 자체가 불필요해진다 |
| **빠른 오브젝트의 섹터 갱신** | 한 프레임에 타일을 건너뛰면 `inSectorObject` 등록이 누락된다. 이동 선분을 훑으면 지나친 타일을 전부 잡는다 |

**게임 루프를 붙일 때 (ROADMAP P2~)**

| 용도 | 비고 |
|---|---|
| **시선 판정 (LOS)** | IR 미사일 락온 유지, 적 AI 시야, 레이더 지형 마스킹. **현재 지형 차폐 판정이 아예 없다** — 산 너머 목표도 그대로 유도된다 |
| **탄도 · 스플래시 판정** | 발사점 → 착탄점 선분을 훑어 최초 지형 충돌 지점을 구한다 |

> 확장 메모: y 축을 더해 3D DDA 로 만들 수도 있지만, 하이트필드에는 **2D 순회 + 타일별 높이 비교**(A.3-③)가 더 싸고 간단하다.
