# 색 관리 재조정 — 설계

three 0.134 → 0.185.1 업그레이드([three-최신화-점검.md](three-최신화-점검.md))의 **남은 절반**.
컴파일·동작은 이미 맞췄고, 여기서는 **화면 색을 다시 맞춘다.**

- 대상 리비전: three **0.185.1** (`node_modules`에서 직접 검증한 사실만 기록)
- 관련 로드맵: [ROADMAP.md](ROADMAP.md) P1-A
- **상태: 페이즈 1~4 이행 완료 (2026-08-07).** 확정값과 실제로 벌어진 일은 [§9 이행 결과](#9-이행-결과)

> §1~§8은 **착수 전에 쓴 설계**다. 사실 관계(§1~§3)는 지금도 유효하지만,
> 계획(§5)과 실제 이행은 몇 군데 갈렸다. 갈린 지점은 §9에 정리했다.

## 0. 결론 요약

1. 렌더러 색 설정이 **소스에 한 줄도 없다.** `outputColorSpace` · `colorSpace` · `toneMapping` 전부 미지정 — 즉 **three 기본값에 전적으로 의존**하고 있는데, 그 기본값이 r134↔r185 사이에 세 번 뒤집혔다.
2. 그 결과 지금 화면은 **경로마다 색 파이프라인이 제각각**이다. 하늘은 뜨고, 지형은 r134 그대로고, 기체는 어둡다. 조명값만 만져서는 절대 못 맞춘다.
3. 방침: **모든 경로를 three 기본 파이프라인으로 통일**한 뒤 조명·노출을 한 번에 조절한다(§4 옵션 B).
4. **r134 색감 복원은 목표가 아니다.** 통일된 상태를 출발점 삼아 **새로 맞춘다.**
   따라서 이전 빌드를 기준으로 삼는 비교(별도 워크트리 + 기준 스크린샷)는 **하지 않는다.**
5. 4개 페이즈. 1~3은 계산으로 값이 나오는 기계적 작업이고, 취향이 들어가는 건 4단계다.
6. **비목표**: r134 색감 복원, 지형에 조명 계산 넣기, dat.GUI 교체, PBR 머티리얼 전환.

## 2. `colorSpace` 태그의 의미 — "바꾸는" 게 아니라 "알려주는" 것

```
NoColorSpace         = ''             ← 텍스처 기본값
SRGBColorSpace       = 'srgb'
LinearSRGBColorSpace = 'srgb-linear'
```

셋 다 별개 값이다. `ColorManagement.getTransfer(NoColorSpace)`는 `LinearTransfer`를 돌려주므로
(`ColorManagement.js:100`) **결과적으로는 선형 취급**이지만, 의미상으로는 "미지정"이다.

`farm.jpg` · `cloud3.png` · 스카이박스 `.bmp` 의 바이트는 **원래부터 sRGB 값**이다.
파일은 한 번도 바뀌지 않았다. 바뀐 건 three가 그 바이트를 **뭐라고 믿느냐**다.

| | three의 해석 | 참/거짓 |
|---|---|---|
| 지금 (태그 없음) | "이 바이트는 이미 선형 값이다" | ✗ 거짓 |
| 태그 후 | "이 바이트는 sRGB 값이다" | ✓ 사실 |

r134에서는 이 거짓말이 문제가 되지 않았다. 출력도 선형이라 **거짓말이 두 번 겹쳐 상쇄**됐다.
r185에서 출력만 sRGB로 바뀌면서 상쇄가 깨진 것이 지금 상황이다.

> `waternormals.jpg`만 예외인 이유도 같은 논리다. 그 파일의 바이트는 색이 아니라 **방향 벡터**라,
> "선형이다"가 원래 참이다. 태그를 붙이면 그때 거짓말이 된다. → **태그하지 않는다.**

## 3. 현재 상태 진단 — 경로마다 다르다

| 경로 | 디코딩 | 인코딩 | 결과 |
|---|:---:|:---:|---|
| **스카이박스** `CubeTexture` | ✗ | **✓** | **감마가 한 번 더** → 허옇게 뜸. 화면 면적 최대 = **체감 주범** |
| 구름 `LowCloud`(`MeshBasic`) | ✗ | ✓ | 위와 동일 |
| 미사일 연기 `MissileFog`(`Sprite`) | ✗ | ✓ | 위와 동일 |
| 미사일 화염 `Missile`(`Sprite`) | ✗ | ✓ | 위와 동일 |
| `ObjectLabel` `CanvasTexture`(`Sprite`) | ✗ | ✓ | 위와 동일 |
| **터레인** `SplattingShader` | ✗ | **✗** | 둘 다 없어 상쇄 → **r134와 픽셀 단위로 동일** |
| **GLTF 모델** | **✓** | ✓ | 유일하게 올바른 파이프라인. 대신 조명 ×π만 잃어 **어두움** |
| `Water` | (normalMap은 데이터라 ✗가 정상) | ✓ | 반사 RT 안에 스카이박스가 들어가므로 스카이박스를 고치면 같이 해결 |
| `Cloud`(GLTF 머티리얼 클론) | ✓ | ✓ | 정상 |
| OBB헬퍼 · AxesHelper 등 순수 `Color` | — | ✓ | hex → 선형 → 인코딩 **왕복이 맞아떨어져 r134와 동일** |

### 3.1 왜 "흐릿"한가 — 수치

조명 ×π 손실(어두워짐)과 출력 인코딩(미드톤 상승)이 **반대 방향**이라, 평균 밝기는 비슷한데 **대비만 뭉개진다.**

디렉셔널 0.6 + 앰비언트 0.5, 정면 조명(dotNL=1) 기준. 램버트 BRDF의 `1/π`까지 포함하면

```
r134 : out = albedo_linear × (0.5π + 0.6π) / π = albedo × 1.100   → 인코딩 없이 그대로
r185 : out = albedo_linear × (0.5 + 0.6) / π  = albedo × 0.350   → sRGB 인코딩
```

| 텍스처 바이트값 | r134 화면값 | r185 화면값 | |
|---:|---:|---:|---|
| 64 | **14** | **36** | 2.5배 들림 |
| 128 | 61 | 78 | 들림 |
| 200 | 162 | **124** | 눌림 |
| 255 | 255 | **160** | 하이라이트 소실 |

**동적 범위 241 → 124.** 거의 절반이다. 이것이 "색감이 흐릿하다"의 정체이며,
각 채널이 중앙으로 몰리므로 **채도 저하도 같은 원인**이다.

> 이 표는 GLTF 모델(`MeshStandard`/`MeshPhong`)에만 해당한다. 터레인은 위 표대로 변화가 없고,
> 스카이박스는 조명을 안 받으므로 계산이 다르다(디코딩 없이 인코딩만 → 단순히 밝아지고 채도가 빠짐).

## 4. 방침 결정

### 옵션 A — r134 색감을 그대로 복원 (기각)

`outputColorSpace = LinearSRGBColorSpace` + `ColorManagement.enabled = false` + 조명 ×π.
한 시간이면 끝나지만 **색 관리를 끄는 것**이라, 앞으로 PBR · 톤매핑 · HDR 하늘 · 포스트프로세싱이 전부 막힌다.
r134에 4년 묶였던 것과 같은 종류의 선택이다. → **기각.**

### 옵션 B — 올바른 파이프라인으로 통일하고 값을 다시 잡기 ★ 채택

통일의 실익은 **노브가 하나로 합쳐진다**는 데 있다.

내장 셰이더는 전부 `<tonemapping_fragment>`를 갖고 있으므로(§1 근거표),
파이프라인을 통일하면 `toneMappingExposure` **하나가 전 화면에 듣는다.**
지금은 이 노브를 돌려도 터레인만 반응하지 않아, 지형과 나머지를 따로 만져야 한다.

단, **조명 강도는 전역 노브가 아니다:**

| | 조명 강도 | `toneMappingExposure` |
|---|:---:|:---:|
| GLTF 모델 · Water | ✓ | ✓ |
| 터레인 · 스카이박스 · 구름 · 스프라이트 | ✗ (unlit) | ✓ |

터레인 스플래팅 셰이더는 조명 계산이 아예 없다(`gl_FragColor = 텍스처 가중합`).
이는 파이프라인을 통일해도 안 바뀌는 **구조 문제**이므로 이번 범위 밖으로 둔다(§7 비목표).

### 4.1 목표 색감 — 복원이 아니라 재설정

옵션 B에는 "무엇에 맞출 것인가"라는 갈림길이 하나 더 있다.

| | 목표 | 판정 방법 |
|---|---|---|
| B-1 | r134 색감을 재현 | 업그레이드 직전 빌드를 워크트리로 띄워 스크린샷 대조 |
| **B-2 ★ 채택** | **기본 파이프라인 상태를 출발점 삼아 새로 맞춤** | 페이즈 간 before/after 비교 + 최종은 저자 판단 |

B-2를 택한 이유는 r134 색감이 **틀린 파이프라인의 산물**이기 때문이다.
거기에 맞추려 하면 통일해 놓은 파이프라인을 다시 왜곡하는 값을 넣게 된다.

이 결정의 실질적 효과:

- **워크트리 · 기준 스크린샷 촬영이 통째로 빠진다** (구 페이즈 0)
- 페이즈 1~3의 합격 기준이 "기준 샷에 근접"에서 **"직전 상태 대비 의도한 변화만 일어났는가"** 로 바뀐다
- 페이즈 3의 π 보정값은 **정답이 아니라 출발점**이 된다 (§5 페이즈 3)
- 페이즈 4가 선택 사항이 아니라 **본 작업**이 된다

**산출물은 커밋하지 않는다.** 저장소 **바깥**의 임시 폴더에 두고 작업이 끝나면 폐기한다.

```
e:\JavaWorkSpace\Sorece\FUN\JW-colorcheck\     ← 저장소 바깥. .gitignore 불필요
```

저장소 안에 두지 않는 이유는 실수로 커밋될 여지를 아예 없애기 위해서다.

### 페이즈 2 — 터레인 ★ 두 변경을 반드시 한 커밋으로  ✅ **완료 · 무변화 확인됨**

스플래팅 텍스처 태그와 셰이더 인클루드는 **각각이 반쪽짜리**다.
디코딩(sRGB→선형)과 인코딩(선형→sRGB)은 서로 역함수라, 하나만 넣으면 한 방향으로만 감마가 걸린다.

텍스처 바이트값 128 기준:

| | 태그(디코딩) | 인클루드(인코딩) | 셰이더가 읽는 값 | 프레임버퍼 | 화면 |
|---|:---:|:---:|---:|---:|---:|
| 지금 | ✗ | ✗ | 0.502 | 0.502 | **128** ✓ |
| 태그만 | ✓ | ✗ | 0.216 | 0.216 | **55** ✗ 훨씬 어두움 |
| 인클루드만 | ✗ | ✓ | 0.502 | 0.735 | **188** ✗ 허옇게 뜸 |
| **둘 다** | ✓ | ✓ | 0.216 | 0.502 | **128** ✓ |

반쪽만 넣은 상태는 이 페이즈의 합격 기준을 **통과할 수 없고**, 커밋하면 화면이 망가진 중간 커밋이 남는다.
파일은 둘(`ShaderManager.ts` / `SplattingShader.ts`)이지만 **논리적으로 하나의 수정**이다.

**(a) 스플래팅 텍스처 5종에 태그** — `farm` `mountain` `factory` `city` `desert`

**(b) 프래그먼트 셰이더에 인클루드 2개 추가** — 순서는 내장 셰이더와 동일하게(`meshbasic.glsl.js:109-111`)

```glsl
gl_FragColor = vec4(0.0, 0.0, 0.0, opacity) + farm + mountain + factory + city + desert;
#include <tonemapping_fragment>
#include <colorspace_fragment>
#include <fog_fragment>
```

**합격 기준** (p1 대비): **육안상 거의 무변화**가 정답.
디코딩과 인코딩이 왕복해 상쇄되므로, 크게 밝아지거나 어두워졌다면 **반쪽만 들어간 것이다.**

허용되는 변화 두 가지:

- 텍스처 전이 구간이 살짝 달라진다 — smoothstep 가중합이 sRGB 공간이 아니라 **선형 공간**에서 일어나게 되므로(이쪽이 물리적으로 옳다)
- fog 경계(샷 C)의 그라데이션이 미세하게 달라질 수 있다

### 페이즈 3 — 조명 π 보정 (출발점 값 투입)  ✅ **완료 — 확정값은 §9**

r134에서 `WebGLLights`가 곱해주던 π가 사라졌으므로 소스에서 되돌려준다.

그 전제를 소스로 옮겨 **같은 조도에서 다시 시작**하려는 것뿐이다.

| 위치 | 현재 | 출발점 |

| `Scene/EditScene.ts` `BuildLight()` 디렉셔널 | 0.6 | **1.885** |

| `Scene/StageScene.ts:35` (현재 비활성) | 1.5 | **4.712** |
| `Scene/StageScene.ts:40` (현재 비활성) | 0.7 | **2.199** |

**합격 기준** (p2 대비): 샷 D의 기체가 **어둡지 않은 정상 노출**로 올라온다.

> 이 시점의 화면이 페이즈 4의 **출발점**이다. 대비가 눌려 보이는 것은 정상이며(§3.1),
> 그것이 페이즈 4가 존재하는 이유다. 여기서 조명값을 감으로 만지지 말 것 —
> 노출·톤매핑과 뒤섞이면 무엇이 원인인지 분리할 수 없게 된다.

### 페이즈 4 — 톤매핑 / 노출로 색감 재설정 ★ 본 작업  ✅ **완료 — 톤매핑은 쓰지 않기로 결정 (§9.3)**

앞의 세 페이즈는 **파이프라인을 옳게 만드는** 기계적 작업이었고, 색감을 만드는 건 여기다.

`WorldManager.CreateRenderer()`에 추가한다.

```ts
this.renderer.toneMapping = THREE.ACESFilmicToneMapping;
this.renderer.toneMappingExposure = 1.0;   // ← 조절 대상
```

조절 노브는 셋뿐이고, **이 순서로** 만진다.

| 순서 | 노브 | 듣는 범위 | 용도 |
|---|---|---|---|
| 1 | `toneMapping` 종류 | 전체 | 하이라이트 롤오프 성격 결정 (§8) |
| 2 | `toneMappingExposure` | **전체** (unlit 포함) | 전역 밝기 |
| 3 | 조명 강도 | GLTF · Water만 | 지형·하늘 대비 **기체만** 밝기 조정 |

3을 마지막에 두는 이유는 범위가 좁아서다. 전역을 먼저 잡고 국소를 나중에 손봐야
"기체를 밝히려다 하늘까지 날려먹는" 왕복을 피할 수 있다.

- 하이라이트 클리핑(§3.1의 255→160 문제)을 해소하는 것이 1차 목적
- 지형 텍스처는 unlit이라 노브 2에만 반응한다. 지형만 따로 밝히고 싶어지면 그건 §7 비목표 영역이다

**합격 기준**: 전 샷에서 저자가 납득. **여기만 정량 기준이 없다** — 그래서 마지막에 둔다.
확정되면 최종 값과 판단 근거를 이 문서에 한 단락으로 남긴다.

### 9.3 톤매핑을 쓰지 않기로 한 근거 ★

`NoToneMapping`은 three 기본값이라 **코드가 없어도 같은 결과**지만, "따져보고 골랐다"를
남기기 위해 `WorldManager`에 명시적으로 적어 두었다.

**톤매핑은 화질 개선이 아니라 밝기 분배 방식의 선택이다.** 1.0을 넘는 값이 실제로 있어야
곡선이 살려낼 정보가 생긴다. 이 씬에는 그런 값이 사실상 없다.

| | 최대 선형값 | 1.0 초과 |
|---|---:|:---:|
| 구름 · 하늘 · 지형 (unlit LDR 텍스처) | ≤ 1.0 | ✗ |
| GLTF 모델 확산광 | `(1 + 1.5)/π × 알베도` ≈ 0.8 × 알베도 | ✗ |
| 물의 태양 반짝임 | `pow(dir,100) × sunColor × 2` → `0xc0c0c0` 기준 **1.05** | 거의 없음 |

반대로 대가는 분명했다. `ACESFilmic`을 켰을 때 **구름이 회색이 되는 현상**이 그것이다:

```
ACES:  color *= exposure / 0.6            // 노출 1 → 1.667배
       a = v*(v + 0.0245786) - 0.000090537
       b = v*(0.983729*v + 0.432951) + 0.238081
       return a / b
```

무채색에 대해 ACES 행렬 두 개는 정확히 항등(각 행의 합이 1.0)이라 스칼라로 계산된다.

| 구름 텍스처 픽셀 | 선형 | ACES 출력 | 화면 |
|---:|---:|---:|---:|
| **255** (순백) | 1.000 | 0.763 | **226** |
| 200 | 0.578 | 0.607 | 204 |

순백만 눌리고 중간톤은 그대로라 **하이라이트와 몸통의 대비가 무너진다.**
곡선이 1.0을 출력하려면 `v ≈ 25.7`(노출 1 기준 선형 15.4)이 필요한데,
구름은 `MeshBasicMaterial`이라 텍스처 값(≤1.0)을 **구조적으로 넘을 수 없다.**

> **다시 볼 시점** — 애프터버너 이미시브 · 태양 글레어/블룸 · 폭발 · HDR 스카이박스가
> 들어오면 1.0을 크게 넘는 값이 생긴다. 그때는 톤매핑이 필요해진다.
> 그 시점의 1순위 후보는 `Neutral`이다 — `peak < 0.76`을 아예 건드리지 않아
> 지금 맞춰 놓은 지형·하늘을 가장 덜 흔든다.

### 9.4 페이즈 1에서 드러난 것 — 물빛

물은 텍스처가 아니라 **`Color` 유니폼**이 문제였다. `Water.js:64`의 `new Color(hex)`가
r152부터 sRGB로 해석돼 선형 변환되면서, 같은 hex가 훨씬 어두운 값으로 들어갔다.

| `0x001e0f` 채널 | r134 유니폼 | r185 유니폼 | |
|---|---:|---:|---|
| G | 0.1176 | 0.0130 | 9.1배 감소 |
| B | 0.0588 | 0.0048 | 12.3배 감소 |

어두운 값일수록 sRGB 곡선이 가팔라 **B가 G보다 더 죽었고**, G/B 비가 2.00 → 2.72로
오히려 더 초록이 됐다. 반면 흰색 항(`sunColor`가 `0xffffff`)은 왕복이 맞아떨어져 그대로였다
→ 색만 죽고 흰색이 남아 **회색**으로 보였다.

물빛 조정의 구조 (벤더 셰이더 `Water.js:203`):

```glsl
albedo = sunColor * diffuseLight * 0.3  +  dot(N,E) * waterColor
//       └── 무채색 바닥 ────────────┘     └── 색조 ──────────┘
바닥 = sunColor^2 * dot(sunDir, N) * 0.5 * 0.3
```

- `waterColor`는 **더하기만** 한다 → 이것만으로는 어둡게 못 만든다. 검푸른 바다는 **바닥을 낮춰야** 나온다
- 바닥의 레버는 `sunColor`이고, `diffuseLight`가 이미 `sunColor`를 품고 있어 **제곱으로** 듣는다
- `sunColor`는 스페큘러에도 쓰여 **반짝임과 채도가 맞바꿈 관계**다
- R은 `waterColor` 기여가 0이라 바닥값이 그대로 남는다 → **바닥이 곧 채도의 상한**

부수 발견: 벤더는 `sunDirection`을 정규화하지 않고 `dot()`에 쓴다(`Water.js:231`).
기존 값 `(1,1,0)`은 길이가 1.414라 **바닥이 41% 부풀어 있었다** — r134에도 있던 버그다. 정규화했다.

확정값 `sunColor 0xc0c0c0` / `waterColor 0x080831` 기준:
바닥 0.0295 + 색조 (0.0024, 0.0024, 0.0307) → 선형 **(0.032, 0.032, 0.060)** → 화면 **(50, 50, 69)**.
수면을 정면에서 내려다볼 때 기준이고, 스침각으로 갈수록 색조 항이 사라져 무채색 바닥만 남는다.

### 9.5 `GUI_Color` 임시 패널

값 하나마다 소스 수정 → 빌드 → 리로드를 도는 비용이 커서 만들었다.
`Tone`(종류·노출) · `Light`(디렉셔널·앰비언트) · `Water`(두 색) + `PrintValues` 버튼.

두 가지 제약을 지켰다.

1. **리프 모듈로 유지** — 프로젝트 모듈을 런타임 import 하면 매니저 싱글턴 SCC(33모듈/130간선)에
   끌려 들어가 `npm run check:cycles`가 실패한다. 조작 대상을 클래스가 아니라 **구조적 인터페이스**
   (`IntensityTarget` / `WaterTuning`)로만 받아 의존이 바깥으로만 흐르게 했다. 기준선 변동 없음.
2. **지우기 쉽게** — `GUIManager`를 일부러 거치지 않았다.
   `EditScene.BuildLight()`의 블록 하나와 파일 하나를 지우면 통째로 빠진다.

dat.GUI 교체 시 함께 걷어낸다 → [ROADMAP.md](ROADMAP.md) P1-A.

> 이행 중 걸린 함정: `EditScene`의 `colorPanel` 필드에 `= null` 초기화식을 붙였더니
> **패널이 두 개 생겼다.** 파생 클래스 필드 초기화는 `super()` 뒤에 실행되는데
> `BuildLight()`는 `SceneBase` 생성자 안에서 이미 불려, 만들어 둔 참조를 덮어썼다.
> `BuildSkyBox`/`BuildObject`/`BuildLight`/`BuildFog`에서 쓰는 필드에는 초기화식을 붙이지 말 것.
